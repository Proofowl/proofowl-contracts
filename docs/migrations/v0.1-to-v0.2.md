# Migration: v0.1 → v0.2

Status: **normative**. Read this before pointing any new work (backend,
indexer, frontend) at this contract.

## The short version

**v0.2 is a new contract with a new API. It is not an upgrade of the
deployed v0.1 testnet alpha instance, and no data moves from one to the
other.** There is nothing to migrate on-chain because there is no
on-chain state that can move — Soroban contracts have no upgrade
mechanism, and no mainnet instance of either version exists.

## Why v0.2 exists

v0.1's per-wallet attestation storage has a measured, unrecoverable
ceiling: 286 attestations succeed for one wallet, the 287th fails
outright (`docs/security/resource-profile-v1.md`). v0.2 replaces that
storage design (`docs/adr/0004-paginated-attestation-storage.md`) and
is a genuinely breaking API change — see
`docs/integration/contract-api-v2.md` for the full new surface and
`CHANGELOG.md` for the itemized diff.

## What does NOT happen

- **v0.1 testnet alpha data does not migrate.** The instance at
  `CCJ7DVU2XYVFNZMHN4VPCYSPJ7HW4RPI544XG5TG42ZX7TDSUIL3SKP6` keeps
  whatever data it has, under the v0.1 ABI, forever (or until it is
  archived/abandoned). `docs/testnet/phase2-alpha.md` and
  `docs/testnet/phase2-retrospective.md` are historical evidence
  records of that instance and are **not rewritten** by this migration
  — they describe what was true about v0.1 at the time, and remain
  accurate as history.
- **No mainnet state exists to migrate.** `PRODUCTION_READINESS.md`
  Gate 6 has never been GO; there has never been a mainnet deployment
  of this contract, v0.1 or v0.2.
- **v0.1's contract ID, WASM, and source are not modified, reused, or
  deployed over.** This work is a local v0.2 candidate only. Deploying
  it to any network — including testnet — requires a separate,
  explicit approval that has not been given as of this document.

## What DOES happen when v0.2 is eventually deployed

- v0.2 gets **a new contract ID**, on whichever network it is deployed
  to, the same way every prior deployment in this project's history
  has (a fresh `stellar contract deploy` with `__constructor(admin,
  attestor)` args — unchanged from v0.1, see ADR 0003). There is no
  `stellar contract upgrade` step and none is planned; this project has
  accepted immutability (`PRODUCTION_READINESS.md` 6.8).
- The v0.2 instance starts with **empty state** — no wallets linked, no
  attestations, no history. Anyone who was linked or had attestations
  on the v0.1 instance is not automatically linked or credited on v0.2;
  they would need to re-run the two-party linking flow and have new
  attestations submitted against the new contract ID, same as any first
  use of the registry.
- If a future decision is made to *carry forward* v0.1's data into a
  v0.2 instance (not decided, not scheduled as of this document), the
  mechanism would be an off-chain backfill, not a contract-level
  migration: v0.1's data is fully public and read-only forever via its
  own getters, so a script could read every known wallet's v0.1 history
  and replay it into v0.2's `submit_attestation` (or an equivalent
  seeding path) one entry at a time. This still needs its own design —
  in particular whether re-emitting historical `AttestationRecorded`
  events on the v0.2 contract at backfill time is desirable for indexer
  continuity, and whether re-attesting already-credited work should
  reuse the same `pr_hash` (making it provably the same contribution)
  or be treated as new — and is explicitly **not designed or
  implemented here**.

## What the backend and frontend must target

**v0.2 only, once it exists and is deployed.** Neither the backend nor
the frontend repository exists yet
(`PRODUCTION_READINESS.md` Gate 4: NO-GO), so this is guidance for
whenever they are built, not a change to a running system:

- Read `docs/integration/contract-api-v2.md`,
  `docs/integration/attestor-protocol-v2.md`, and
  `docs/integration/event-indexer-v2.md` — not the `-v1` equivalents,
  which describe an API that no longer matches this crate's `src/lib.rs`
  and are kept only as the historical record of what v0.1 was.
- Use `sdk/typescript`'s pagination helpers
  (`getAttestationCount`, `getAttestation`, `getAttestationsPage`) —
  the SDK's `getAttestations` (unbounded) helper is removed in the same
  commit that removes the contract function it wrapped.
- Schedule **paginated** TTL keep-alive sweeps
  (`bump_wallet_core_ttl` + repeated `bump_wallet_attestations_ttl_page`
  calls), not a single per-wallet call — see
  `docs/integration/event-indexer-v2.md` §6 for the exact scheduling
  responsibility this places on whichever service ends up owning it.

## v0.1's place going forward

v0.1 remains exactly what Phase 2/3 established it as: **historical
test evidence that the contract pattern (two-party linking,
attestor-resolved crediting, global PR dedup, TTL-maintained storage)
works end-to-end on real Stellar testnet infrastructure.** It is not,
and after this migration document is not retroactively claimed to have
been, an integration target for any future component. `README.md`'s
"Deployed contracts" table keeps the v0.1 testnet alpha row unchanged;
a v0.2 row is added only once (and if) a v0.2 instance is actually
deployed under the separate approval this document's introduction
requires.

## The Phase 4 finding's status

`docs/security/known-risks-v1.md` R1 ("per-wallet attestation storage
has a hard, unrecoverable ceiling") is updated to: **resolved in the
local v0.2 candidate, pending validation and a new testnet
deployment.** "Resolved" describes the storage design and the tests
proving it in this repository today; it does not claim v0.2 has been
deployed, audited, or exercised against a live network — none of those
things are true yet. The original v0.1 measurement (286 / 287) is kept
in `docs/security/resource-profile-v1.md` unedited, as the evidence
record that justified this redesign; `docs/security/resource-profile-v2.md`
is the new, separate record for v0.2.
